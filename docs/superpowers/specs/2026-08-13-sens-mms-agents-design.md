# SENS MMS 워크플로우 AGENTS.md 설계

## 목적과 범위

이 문서는 네이버클라우드 Simple & Easy Notification Service(SENS)를 이용해 수신번호별로 MMS를 발송하는 프로젝트의 `AGENTS.md` 설계를 정의한다. 이후 에이전트는 발송 코드 작성, 시험, 실제 실행 시 이 규칙을 따라야 한다.

이 단계의 산출물은 프로젝트 운영 규칙인 `AGENTS.md`다. 실제 발송 프로그램 구현과 실발송은 별도 작업이며, 사용자의 명시적 승인 없이 수행하지 않는다.

## 공식 명세

작업 시작 전 다음 최신 공식 문서를 확인한다.

- 메시지 발송: <https://api.ncloud-docs.com/docs/sens-sms-send>
- 메시지 발송 목록 조회: <https://api.ncloud-docs.com/docs/sens-sms-list>
- 메시지 발송 결과 조회: <https://api.ncloud-docs.com/docs/sens-sms-get>
- 첨부 파일 업로드: <https://api.ncloud-docs.com/docs/sens-sms-attachment-create>
- SENS 공통 인증 및 응답: <https://api.ncloud-docs.com/docs/sens-overview>

명세가 이 문서와 달라진 경우 실제 발송을 중단하고 차이를 사용자에게 보고한다. 명세를 확인하지 않은 상태에서 API 요청 형식이나 성공 기준을 추정하지 않는다.

## 프로젝트 입력

### 수신번호

- 기준 파일은 프로젝트 루트의 `receiving_numbers.csv`다.
- 현재 파일은 확장자와 달리 탭으로 구분되어 있으므로 쉼표와 탭을 자동 감지한다.
- `number` 열은 필수이며 `name` 열은 선택이다.
- 전화번호는 문자열로 읽어 선행 `0`을 보존한다.
- 앞뒤 공백과 하이픈을 제거한 뒤 숫자만 남아야 한다.
- 정규화 후 같은 번호가 여러 번 존재하면 한 번만 발송한다.
- 빈 번호나 형식 오류는 API를 호출하지 않고 `FAILED`로 기록하며 `attempts=0`으로 둔다.
- 수신번호와 이름은 로그나 오류 출력에 평문으로 노출하지 않는다. 필요한 경우 마지막 네 자리만 표시한다.

### MMS 이미지

- 이미지 디렉터리는 프로젝트 루트의 `mms_img`다.
- JPG 또는 JPEG 이미지가 정확히 두 개 있어야 한다.
- 각 파일은 300KB 이하이고 해상도는 1500×1440 이하여야 한다.
- 현재 발송 순서는 `mms_01_intro.jpg`, `mms_02_details.jpg`다.
- 두 이미지는 실행당 한 번씩 업로드하고 반환된 `fileId`를 같은 실행의 모든 수신번호에 재사용한다.
- SENS 요청의 `files` 배열에도 위 순서를 유지한다.
- 두 이미지의 좌우 표시 여부는 수신 단말과 메시지 앱이 결정하므로 워크플로우가 보장한다고 표현하지 않는다. 워크플로우는 첨부 순서만 보장한다.

### 메시지 본문

다음 본문을 줄바꿈까지 그대로 사용한다.

```text
[개업소연 안내]

안녕하세요.
세무사 윤성중 입니다.
6월 말일자로 국세청에서 퇴직하고 호연회계법인에서 새로 시작하게 되었습니다.
많은 응원 부탁드립니다.

감사합니다.
```

- `type`은 `MMS`다.
- 별도 `subject`는 넣지 않는다.
- 본문을 임의로 고치거나 광고 문구를 자동 삽입하지 않는다.
- `contentType`의 광고성 여부가 확정되지 않았다면 실발송 직전에 중단하고 사용자 확인을 받는다.
- 광고성 메시지라면 관련 법령과 SENS 정책을 확인하고 필요한 표시를 갖춘 별도 승인 문안 없이는 발송하지 않는다.

## 인증 정보와 실발송 안전장치

- Access Key, Secret Key, SENS 서비스 ID, 등록된 발신번호는 환경변수나 승인된 비밀 저장소에서만 읽는다.
- 비밀값을 코드, `AGENTS.md`, 테스트 데이터, 로그, `result.csv`에 기록하지 않는다.
- API 서명은 공식 HMAC-SHA256 명세대로 매 요청 시 생성한다.
- 실제 발송 전 수신 건수, 마스킹된 번호 표본, 발신번호, 본문, 첨부 파일명과 검증 결과를 사용자에게 제시한다.
- 사용자가 해당 실행의 실발송을 명시적으로 승인하기 전에는 드라이런과 모의 API 검증만 수행한다.
- 테스트 및 검증 과정에서 실제 전화번호로 발송하지 않는다.

## 발송 단위

- SENS가 한 요청에서 최대 100개 수신번호를 지원하더라도 이 워크플로우는 배치 기능을 사용하지 않는다.
- 수신번호마다 독립적인 POST 요청을 만든다.
- 각 요청의 `messages` 배열에는 하나의 `to`만 포함한다.
- 이미지 두 개의 `fileId`는 모든 단건 요청에 동일하게 첨부한다.
- 수신번호 하나의 상태가 다른 번호의 처리 결과를 덮어쓰지 않도록 번호별 상태를 독립 관리한다.

## 상태 모델

각 수신번호는 다음 세 가지 최종 또는 보류 상태 중 하나를 갖는다.

| 상태 | 의미 | `is_sent` | 자동 신규 발송 |
| --- | --- | --- | --- |
| `SENT` | `COMPLETED + success` 확인 | `true` | 금지 |
| `FAILED` | 명시적 실패가 확인되고 현재 승인된 발송 실행의 총 3회 소진 | `false` | 사용자가 별도 재발송 실행을 명시한 경우만 허용 |
| `PENDING_CONFIRMATION` | 접수 또는 최종 결과가 아직 불확실 | 빈 값 | 금지 |

`PENDING_CONFIRMATION`은 실패가 아니다. 결과 미확정 건을 `is_sent=false`로 기록하지 않는다.

## 발송과 결과 확인 흐름

1. 기존 `result.csv`가 있으면 먼저 읽는다.
2. `SENT` 번호는 건너뛴다.
3. `PENDING_CONFIRMATION` 번호는 새로 발송하지 않고 저장된 `request_id` 또는 `message_id`로 기존 요청부터 조회한다.
4. 이전 실행의 `FAILED` 번호는 사용자가 해당 실패 번호의 재발송을 명시한 경우에만 새 실행 대상으로 포함한다.
5. 대상 번호에 MMS 단건 발송 요청을 보낸다. 실제 POST 호출 한 번을 한 번의 발송 시도로 계산한다.
6. POST 응답의 `statusCode="202"`는 접수 성공으로만 취급하고 최종 발송 성공으로 취급하지 않는다.
7. 응답의 `requestId`를 즉시 저장한다.
8. 발송 목록 조회에 `requestId`를 사용해 수신번호의 `messageId`를 얻고 즉시 저장한다.
9. 30초마다 결과 조회 API를 폴링한다.
10. `messages[].status="COMPLETED"`이면서 `messages[].statusName="success"`이면 `SENT`로 확정한다.
11. `COMPLETED + fail`이면 명시적 실패로 처리한다. 총 발송 시도가 3회 미만이면 30초 후 새 발송을 시도하고, 3회째에도 실패하면 `FAILED`로 확정한다.
12. `READY` 또는 `PROCESSING`은 실패가 아니므로 같은 요청을 계속 조회한다.
13. 한 발송 요청이 10분 동안 종결되지 않으면 `PENDING_CONFIRMATION`으로 저장하고 해당 번호에 대한 새 발송을 금지한다.
14. 이후 실행에서는 같은 요청을 먼저 재조회한다. 나중에 성공이 확인되면 `SENT`, 명시적 실패가 확인되면 남은 발송 횟수에 따라 재시도 또는 `FAILED`로 전환한다.

## 모호한 요청 결과 처리

다음은 명시적 실패가 아니라 결과 불확실 상태다.

- POST 요청 중 클라이언트 네트워크 타임아웃
- 연결 종료로 HTTP 응답을 받지 못한 경우
- 결과 조회 API의 일시적 오류
- `requestId`는 받았지만 `messageId`를 아직 찾지 못한 경우
- `READY` 또는 `PROCESSING`이 10분을 초과한 경우

이 경우 즉시 재발송하면 원래 요청이 나중에 성공하여 중복 MMS가 전달될 수 있다. 따라서 `PENDING_CONFIRMATION`으로 저장하고 신규 발송을 막는다. 식별자가 없는 모호한 POST 요청은 요청 시각과 수신번호를 이용해 발송 목록을 조회하되, 기존 요청을 유일하게 식별할 수 없으면 자동 재발송하지 않고 수동 확인 대상으로 남긴다.

## 재시도 규칙

- 사용자가 승인한 한 번의 발송 실행 안에서 최초 발송을 포함해 수신번호당 최대 3회다.
- 명시적인 POST 실패 또는 `COMPLETED + fail`일 때만 발송 재시도를 허용한다.
- 접수 여부가 불확실한 네트워크 오류, 비종결 상태, 조회 오류는 발송 재시도 사유가 아니다.
- 재시도 전 30초를 기다린다.
- 세 번째 명시적 실패의 `statusCode`와 `statusMessage`를 최종 오류로 보존한다.
- 한 실행이 끝난 뒤 `FAILED` 번호를 별도 발송 실행으로 다시 보내려면 사용자가 대상을 명시적으로 승인해야 한다.
- 별도 재발송 실행을 시작하기 전에 기존 `result.csv`를 타임스탬프가 포함된 보관 파일로 복사하여 이전 3회의 결과를 보존한다.
- 별도 재발송 실행에서 승인된 `FAILED` 번호의 `attempts`는 0부터 다시 계산한다. `PENDING_CONFIRMATION`은 별도 실행 대상으로 전환하거나 횟수를 초기화하지 않는다.

## 결과 파일

결과는 프로젝트 루트의 `result.csv`에 UTF-8로 저장한다. 한 번호당 한 행을 유지하며 상태가 바뀔 때마다 안전하게 갱신한다. 기존 파일을 무조건 초기화하지 않는다.

열은 다음과 같다.

| 열 | 값 |
| --- | --- |
| `receiving_number` | 정규화된 수신번호 |
| `delivery_status` | `SENT`, `FAILED`, `PENDING_CONFIRMATION` |
| `is_sent` | 성공 `true`, 최종 실패 `false`, 미확정 빈 값 |
| `attempts` | 현재 승인된 발송 실행에서 발생한 실제 POST 발송 요청 횟수 |
| `request_id` | 현재 또는 마지막 발송 요청 ID |
| `message_id` | 현재 또는 마지막 메시지 ID |
| `error` | `null` 또는 JSON 문자열 `{"status":"...","message":"..."}` |

상태별 결과는 다음과 같다.

- `SENT`: `is_sent=true`, `error=null`
- `FAILED`: `is_sent=false`, `error`에 최종 명시적 실패의 상태와 메시지 기록
- `PENDING_CONFIRMATION`: `is_sent`는 빈 값, `error=null`, 가능한 식별자 보존
- 입력 검증 실패: `delivery_status=FAILED`, `is_sent=false`, `attempts=0`, `error.status=VALIDATION_ERROR`

CSV 저장 중 중단되어 기존 결과가 손상되지 않도록 임시 파일에 완전한 내용을 쓴 뒤 같은 디렉터리에서 원자적으로 교체한다.

## 재실행과 조정

재실행은 새 발송보다 기존 상태 조정을 먼저 수행한다.

1. `result.csv`를 읽는다.
2. 모든 `PENDING_CONFIRMATION` 건의 기존 요청을 조회한다.
3. 확정된 결과를 `SENT` 또는 명시적 실패 상태로 갱신한다.
4. 여전히 미확정인 번호에는 새 MMS를 보내지 않는다.
5. `SENT` 번호는 항상 제외한다.
6. 사용자가 승인한 신규 번호와 명시적으로 승인한 `FAILED` 번호만 발송 단계로 넘긴다.
7. `FAILED` 번호의 별도 재발송 실행이라면 기존 `result.csv`를 보관한 뒤 해당 대상의 `attempts`를 0으로 초기화한다.

이 순서가 `15분 뒤 성공했지만 10분 시점에 실패로 기록되어 다시 보내는` 중복 발송 시나리오를 방지한다.

## 검증 전략

실제 SENS 발송 없이 모의 응답으로 다음 상태 전이를 검증한다.

- `202 → PROCESSING → COMPLETED/success → SENT`
- 첫 번째 명시적 실패 후 두 번째 성공
- 세 번의 명시적 실패 후 `FAILED`
- 10분 초과 후 `PENDING_CONFIRMATION`, 이후 재조회에서 성공
- POST 응답이 유실된 모호한 접수 상태
- 결과 조회 API의 일시적 오류
- 재실행 시 `SENT`와 `PENDING_CONFIRMATION` 번호를 건너뛰는 동작
- 중복 수신번호가 한 번만 발송되는 동작
- 입력 번호 및 이미지 검증 실패가 API 호출 전에 차단되는 동작
- `result.csv` 재기동 및 원자적 갱신 동작

## 현재 프로젝트 상태

- `receiving_numbers.csv`가 존재하며 현재 탭 구분 형식이다.
- `mms_img/mms_01_intro.jpg`는 1080×1440, 약 245KB다.
- `mms_img/mms_02_details.jpg`는 1080×1440, 약 267KB다.
- 두 이미지는 현재 SENS 업로드 제한 범위에 들어온다.
- 현재 디렉터리는 Git 저장소가 아니므로 이 설계 문서를 커밋할 수 없다.
